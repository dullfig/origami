The number that actually answers your question

2.2 MB of Rust is roughly 700k tokens. Which means the entire AgentOS codebase already fits in a 1M context window unfolded, with room left over.

So "load the whole codebase with every function folded" isn't solving a capacity problem — it can't be, because there isn't one at this size. If folding is worth doing here, it's for a different reason, and it's one your own README already argues:

▎ every irrelevant token degrades the thinker. Focused 300 tokens beats full 128K history.

That's the real case. Not "it won't fit" but "700k tokens of mostly-irrelevant code competing for attention makes the model worse at the one function it needs." Which is a claim you'd want to measure rather than assume, and it's measurable — same harness, same task, folded vs. unfolded.

Assuming ~40 tokens per stub (signature plus a one-line purpose — Rust signatures are wordy).

Two things fall out of that:

Excluding tests is free and halves the index. 1,404 of 2,854 are test functions. You essentially never need test_boundary_burst in a navigational index, and dropping them costs nothing.

Function-level across a whole repo is not obviously the right default. 114k tokens of index is a large working session's entire budget spent before you've done anything. File-level is 12× cheaper and probably captures most of the navigational value — you usually need "which file," and once you're in the file you can read it. Function-level earns its cost when the task is cross-cutting: blast radius, who-calls-what, does-this-helper-already-exist.

Which suggests the interesting design isn't one fold level — it's folding at different granularities in the same context. Crate-level for the 20 crates you're not touching, function-level for the two you are.

Two connections worth noting

This is project_two_tier_memory with a different substrate. Synopsis tier that's always scanned, source tier you drill into on demand — the fold is the synopsis, the unfold is the drill. Same shape as the pin bank's own descriptions-then-bodies protocol, which is how I cold-started this project in the first place.

And more interesting: origami is the token-level prototype of what you wanted to build at the KV level last month. Fold = evict from context, keep a stub. Unfold = re-insert and re-prefill. The composable-KV version keeps the computed attention instead of re-prefilling — same policy, cheaper mechanism.

That ordering is lucky. If origami's fold policy proves out at the token level, the KV version stops being a speculative build and becomes a performance optimization of a policy you've already validated. Worth letting origami run first for that reason alone.

Shower-thought or not, there's a strong version of it — and the strong version fixes the exact problem I hit twenty minutes ago.

What it actually solves

When I hydrated fold-016, the whole fold came into my context. The anchor didn't slice it. For a small fold that's free; for fold-006 (110 KB of pin descriptions) it'd be ~28k tokens to answer one question.

A fold-agent inverts that: the content never enters the orchestrator's context at all. I ask "does your chunk branch on tenant name?" and get back a sentence, not an artifact. That's not a marginal improvement over hydrate — it removes the transport cost entirely, and it makes anchor-slicing unnecessary rather than merely better.

That reframes the idea: it's less "an agent owns a chunk" and more "hydrate returns an answer instead of a document."

Where it breaks, and it's the same wall as last month

Bugs live in the seams, not in the chunks. If a bug were contained in one fold you'd probably have found it already. The ones that need hunting are interaction bugs: A hands B something B didn't expect, or two chunks disagree about an invariant.

An agent that owns only fold-A structurally cannot see that. It has exactly the cross-chunk blindness we characterized for composable KV — a chunk computed without the others in view, answering confidently about a world it can only partly see. Same failure, one layer up the stack. And the same sharp edge: each agent gives a locally correct answer, and the composition of locally correct answers is wrong.

So a naive fold-per-agent debugging swarm has a predictable failure mode: forty-three agents each report "not me," and the bug is in the handshake nobody owns.

The fix is the split you've been applying all week

Keep interfaces central; distribute implementations.

- The orchestrator holds the signatures and call graph — who calls what, with what types. That's cheap: the function index from earlier, or far less if you keep only edges.
- Fold-agents hold bodies.

Then the orchestrator can reason about the seam — which is where the bug is — and dispatch body-level questions to whoever owns the relevant implementation. That's the same inversion as ports/security, and the same one as "AgentOS declares inference, doesn't own it." Interface up, implementation out.

You already have both halves as capabilities: ripwire does blast-radius and who-calls-what, and treesitter does symbol extraction. The call-graph tier isn't speculative.

Two smaller cautions

Don't eager-spawn. 43 folds is 43 contexts, each re-establishing itself and reporting back — the delegation-overhead problem. Spawn on suspicion, from the call graph, not on fold creation.

Read-only is most of the value and none of the risk. "In charge of" could mean answers questions, or could mean edits. Forty-three agents writing to one tree is the coordination problem your multiagent guidance specifically warns about. Question-answering fold-agents get you the debugging win without it.

And keep the topology a star, not a mesh. Agents reporting to a coordinator preserves the audit trail and keeps the platform in the middle of every hop — peer-to-peer chat scales n² and makes provenance hard, which is a line your protocol already holds elsewhere.

The cheap test

Before any agent infrastructure: the whole idea rests on one claim — that a worker answering questions about a fold beats hydrating the fold. That's testable today with a single subagent and zero new machinery. Give one agent one fold, ask it three questions you'd otherwise have hydrated for, compare answer quality and token cost against just pulling the fold.

If it wins, the architecture question becomes worth having. If it doesn't, you've saved yourself building a swarm — and you'd have learned it in an afternoon, which is the same shape as the placebo-note ablation and the KV-divergence probe. You've got a good habit going of finding the one measurement that makes the expensive build unnecessary.

Your two-bar framework maps onto this cleanly, and it sets the quality target:

- Editing is Bar 2. Exact bytes, no drift tolerated.

Which means the fold-agents can be Haiku-class and still work, because a ranking function tolerates noise that a generator doesn't. Cheap and parallel for the scatter, expensive and serial for the commit — your hybrid-routing doctrine, applied at a new layer.

The sharp edge: origami acquires the bug it was built to fix

The main agent edits a file. That file's fold is now stale. So is any fold-agent holding it. Ask a question ten minutes later and you get an answer about code that no longer exists.

That is precisely the stale-file-in-context problem that started the composable-KV thread — a superseded version still answering questions as though current. Origami reproduces it internally the moment writes enter the loop.

The good news is that single-writer makes it tractable: exactly one actor mutates, so you always know when to invalidate and what. A mesh of editing agents would make this nearly unsolvable; your design makes it a hook. But it has to be wired deliberately — invalidate on write, and decide whether a stale fold-agent gets killed or re-briefed.

Two smaller disciplines

Hydrate wider than the plan. The agents told you where they think it is, under blindness. Pull the callers and callees of the change site, not just the change site — blast radius, which is what ripwire already does. The extra tokens are cheap relative to editing the wrong thing.

Be willing to throw the plan away at hydrate time. The plan is formed from reports; the artifact may contradict them. When it does, that's the system working — the artifact corrected the paraphrase — but only if the main agent treats the mismatch as information rather than as an obstacle to route around. Worth making it an explicit step: after hydrating, check the plan's premises against the real code before the first edit.

That last one is the same failure mode as accepting a code review you haven't verified. The pattern keeps recurring: a cheap lossy signal proposes, an expensive exact source disposes, and the whole thing works only if the expensive step is genuinely allowed to overrule.

> aha! point well taken! that is a central issue that needs fixing. how to track changes in files you already folded

Right. Let me lay out the design space, because the answer isn't one mechanism — it's a few, and they cover different holes.

First: folds aren't uniformly invalidatable

Classify at fold time, because the strategies differ:

┌──────────────────────────────────────┬─────────────────────────────────┬────────────────────────────────────────┐
│              fold kind               │           stale when            │               trackable?               │
├──────────────────────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ file read (Read, cat, sed -n)        │ that file changes               │ cheaply — path + hash                  │
├──────────────────────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ search result (grep, rg)             │ any file in the searched set    │ hard — wide blast radius               │
│                                      │ changes                         │                                        │
├──────────────────────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ command output (git log, test run,   │ almost any change               │ not really — it's a timestamped        │
│ build)                               │                                 │ observation                            │
├──────────────────────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ pinned read (git show <sha>:file)    │ never                           │ immutable, mark it so                  │
└──────────────────────────────────────┴─────────────────────────────────┴────────────────────────────────────────┘

That last row matters more than it looks: a meaningful fraction of folds are immutable by construction and should be exempt from the whole machinery.

Two mechanisms, and you need both

Hook the writer. Single-writer is what makes this tractable — the main agent's edit tool knows exactly which path it touched, so on write you look up folds covering that path and mark them. Precise, instant, zero false positives.

Hash sweep. The hook misses everything out-of-loop: you editing in your IDE, a build regenerating a file, git checkout, another Claude session. So fold-time you record path + content hash; on sweep you re-stat and compare. Use a hash, not mtime+size — a one-character code edit preserves size, and that's the common case.

Neither alone is sufficient. The hook is precise but blind outside the loop; the sweep is comprehensive but coarse.

Granularity: this is the real argument for function-level folds

You asked at the top of the session whether to fold every function. I answered on compression grounds and said file-level was probably the better default. Invalidation is a better argument than compression was.

Edit one function in a 600-line file: a file-level fold goes entirely stale, and you lose the other twenty functions' summaries for no reason. A function-level fold invalidates one entry out of 2,854 and leaves the rest valid.

So the granularity question has a better answer than "how much does it compress." It's how much does one edit destroy.

Three tiers of staleness, not one

Text-level invalidation is necessary but not sufficient — this is the seam problem again:

- Body changed, signature same → callers are fine. Don't touch them.
- Signature or type changed → callers' text didn't change, but their folds' descriptions may now be wrong. Flag as suspect, don't hard-invalidate.
- Deleted or renamed → hard invalidate, plus callers are suspect.

You have treesitter for symbol extraction and ripwire for who-calls-what, so the call-graph tier isn't speculative — it's assembling two things that exist.

⚠️ The invalidation must be visible in the rendering

This is the part I'd get wrong if I were building it, so let me be emphatic: marking a fold stale on disk does nothing for me. If the stub still reads as a confident advertisement, I'll use it as one. I have no way to detect that the underlying file moved — that's the exact self-reporting blindness from earlier.

The stub itself has to carry it:

[origami fold-012 · ⚠️ STALE — file changed after your edit at 07:23 · hydrate for current]

A silently-stale fold is strictly worse than no fold, because it converts "I don't know" into "I confidently know something outdated."

Fold-agents: kill, don't re-brief

If a fold-agent holds the content and the fold goes stale, the agent is stale — the old text is sitting in its context. You can't mark an agent stale; you either kill it or re-brief it.

Kill it. Re-briefing means surgically replacing the stale span in a live context while keeping everything after — that's the splice problem, the hard one. Killing and respawning is truncate-and-restart, the easy one. You concluded three weeks ago to build truncate before splice; this is the same fork, and the same answer.

Respawn is cheap anyway: the agent's whole job is to re-read one fold and answer questions about it.
